## Comment 4 — Default visibility
**My position:** I'm keeping `public = db.Column(db.Boolean, default=True)` (`models.py:80`) as the default for `WatchlistEntry`. I don't think this is a neutral default that happens to be `True` — it's a deliberate choice, and I'd defend it in review rather than quietly flip it to `False` to be "safe."

**Reasoning — what I'm optimizing for:** CineLog's watchlist is a social/discovery feature, not a private utility list. The entire value of a watchlist over, say, a personal notes file is that other people can see it: friends browsing what you want to watch, recommendation surfaces built on aggregate public watchlists, "people who added this also added..." type features later. If `public` defaults to `False`, every single entry a user adds is invisible until they take a second, separate action (a settings toggle, or a per-entry flag) to make it visible. That means the *default first-run experience* of the feature is "you added 10 films to your watchlist and none of them do anything socially" — which kills the feature's core loop before the user has any reason to know the toggle exists. Defaulting to `True` means the social/discovery value is realized automatically, on the very first `add_to_watchlist` call, with zero extra steps. I'm optimizing for time-to-value on the feature's actual purpose, not for the theoretical user who wants privacy by default but hasn't asked for it.

**Tradeoff acknowledged:** The real cost here is consent, not just "privacy is nice to have." A user adding a film to their watchlist is not necessarily choosing to broadcast it — they might be planning what to watch with a partner, tracking something for a work reason, or adding a title they'd be embarrassed to have show up in a friend's feed, and none of that is visible to them at add-time because there's no confirmation step or visible indicator in `add_to_watchlist()` (`services/watchlist_service.py`) that the entry is being created as public. That's a legitimate surprise-and-embarrassment risk, and "the user could just toggle it off" isn't a real mitigation if they don't know the toggle exists or that they need to. If this ships as-is, I'd want a corresponding UI change (a visible "public" indicator at add-time, or a one-time onboarding notice) to close that gap — the tradeoff I'm accepting is discoverability-by-default in exchange for needing that follow-up UX work, not a free lunch.

**Counterargument I hadn't fully weighed:** The two failure modes of this default aren't symmetric, and my reasoning above treats them as if they were. If a user wanted their watchlist public and it defaulted private, the fix is trivial and fully reversible — flip a toggle, nothing lost. If a user wanted it private and it defaults public, by the time they discover the toggle, friends may already have seen it — that harm can't be undone. A careful reviewer would say defaults should be chosen by which failure mode is recoverable, not by comparing engagement upside to embarrassment downside as if they're the same currency. Relatedly, I framed the UI mitigation (a visible indicator/onboarding notice) as something I'd merely "want" alongside shipping `public=True` — not as a blocking condition. That's exactly how unmitigated defaults ship permanently: the safeguard becomes follow-up work that never lands, and the consent gap I flagged stays open indefinitely. And the "time-to-value" argument I used to justify the default mostly benefits users who already understand CineLog's social norms — it's new users, who don't yet know the watchlist is visible, who are most exposed to the default I'm optimizing away from protecting.

## Comment 5 — Sort order
**My position:** I implemented the maintainer's preference: `get_watchlist()` now sorts by `date_added` descending (most recently added first), matching `get_collection()`'s existing `order_by(CollectionEntry.date_added.desc())` in `services/collection_service.py`. I'd previously left `get_watchlist()` sorting by `Film.title.asc()` (alphabetical), and on reflection I think that was the wrong call, not just a stylistic difference from collection.

**Reasoning:** The maintainer's point, as I understand it, is that a watchlist isn't a catalog you browse — it's a queue of intent, and the two entries most relevant to "what am I actually going to watch" are the one you just added and the one you added five minutes before that. Alphabetical order throws that signal away and replaces it with an ordering that has nothing to do with why the film is on the list. It also made the watchlist behave differently from the collection for no functional reason — both are `user_id, film_id` join tables with a `date_added` column already sitting right there (`models.py:57` and `models.py:79`); sorting one by title and the other by date was an inconsistency a user switching between the two views would actually notice, not a deliberate design choice I can defend.

**Engagement with reviewer's point:** Where I'd push back slightly, if this were still open for debate, is that alphabetical isn't strictly worse in every case — it's genuinely better once a watchlist gets long (50+ films) and a user is scanning for a specific title rather than deciding "what's next." But that's a search/filter problem, not a default-sort problem, and CineLog doesn't have a search-within-watchlist feature yet, so optimizing the default sort for a browsing use case the app doesn't support yet isn't a good tradeoff today. If that changes, I'd want a separate sort toggle rather than reopening this default. I verified the change with `test_get_watchlist_returns_newest_first` in `tests/test_watchlist.py`, modeled on `test_get_collection_returns_newest_first` in `tests/test_collection.py`: two films added five days apart, asserting the later one comes first in the returned list. That test also caught a real bug while I was in there — `get_watchlist()` was calling `entry.film.to_dict()`, but `WatchlistEntry` has no `film` relationship/backref defined on it (unlike `CollectionEntry`, which gets one via `Film.collection_entries`'s backref), so every call to `get_watchlist()` was raising `AttributeError` regardless of sort order. I fixed it with `db.session.get(Film, entry.film_id).to_dict()`, mirroring the lookup pattern already used in `add_to_watchlist()`, rather than adding a new backref to the shared `Film` model.

**Counterargument I hadn't fully weighed:** I bundled a correctness bug fix (`entry.film` `AttributeError`) into the same change as a design preference (sort order). Those are different kinds of changes with different risk profiles, and now they can't be reviewed or reverted independently — if someone wants to reopen the sort-order debate, they can't revert just that without also reverting a bug fix they'd obviously want to keep. A careful reviewer would flag that as scope creep, even though the fix was small. Separately, my "consistency with collection" argument assumes the two lists are the same kind of thing, and they're not: collection is a historical log where `date_added` means "when I logged that I watched this," and recency is the right signal there. Watchlist is a queue of future intent — `date_added` there only means "when I clicked add," which is a weak proxy for what someone actually wants to watch next (a whim addition from five minutes ago outranks a film they've wanted to see for a year). I treated cross-feature consistency as decisive, but a reviewer could reasonably say the two features have different semantics and shouldn't inherit the same sort key just because the column is named the same thing. The more honest framing is that both alphabetical and date-added are proxies for something the schema doesn't capture — explicit user-assigned priority — and picking a winner between two imperfect defaults isn't the same as solving the actual need.
